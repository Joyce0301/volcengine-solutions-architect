# 火山引擎架构顾问 Skill / Subagent 设计

日期：2026-08-08  
状态：待用户书面审核  
目标平台：Codex 原生；保留跨平台扩展接口

## 1. 目标

交付一个可安装、可分享的 Codex Plugin。用户提出业务需求后，通过其中的主 Skill 获得基于火山引擎全产品体系的架构方案。方案覆盖 AI 与 Agent、普通云原生、大数据、数据库与存储、网络与安全、音视频与边缘等场景。

Skill 必须先输出需求缺口清单，只追问会改变产品选择或部署拓扑的问题；随后按场景路由领域分析，最终交付有假设、有证据、有取舍且可继续实施的架构设计。

## 2. 非目标

第一版不执行以下工作：

- 创建、修改或删除真实火山引擎资源。
- 代替火山引擎官方对产品能力、SLA、合规或商务条件作出承诺。
- 在缺少用量和官方价格信息时生成精确报价。
- 直接生成 Terraform、Pulumi 或其他基础设施代码。
- 默认输出 Draw.io、PPTX 或其他二进制交付物。
- 为每个火山引擎产品维护完整静态 API 或规格镜像。

## 3. 设计原则

1. 业务需求先于产品名称：先明确能力和约束，再映射火山引擎产品。
2. 事实、假设、推断和待验证项严格分离。
3. 稳定分类可内置，动态事实必须在线核验。
4. 多代理是质量和速度优化，不是安装或运行的硬依赖。
5. 主 Skill 对最终方案负责；subagent 不直接向用户交付彼此割裂的方案。
6. 无法核实时保留不确定性，不用模型记忆伪造精确事实。
7. 默认输出应可版本管理、可复制、可审查并便于跨平台迁移。

## 4. 交付形态

```text
volcengine-architecture/
├── .codex-plugin/
│   └── plugin.json
└── skills/
    └── design-volcengine-architecture/
        ├── SKILL.md
        ├── agents/
        │   └── openai.yaml
        ├── references/
        │   ├── intake-contract.md
        │   ├── routing-matrix.md
        │   ├── architecture-output.md
        │   ├── product-catalog.md
        │   ├── ai-and-agent.md
        │   ├── compute-cloud-native.md
        │   ├── data-analytics.md
        │   ├── database-storage.md
        │   ├── networking-security.md
        │   ├── media-edge.md
        │   └── subagent-contracts.md
        └── scripts/
            └── validate-deliverable.py
```

Plugin 是安装和分享边界，主 Skill 是唯一用户入口。`agents/openai.yaml` 仅提供 Skill 的 Codex UI 元数据。领域角色通过 `subagent-contracts.md` 定义，并由主 Skill 在当前运行环境具备多代理能力时进行调度；不要求接收方预装自定义 agent TOML。

所有平台无关的输入、输出和角色协议均使用 Markdown 中的稳定字段定义。未来适配其他 Agent 平台时，只替换安装清单和调度适配层，不改变业务需求模型及架构输出契约。

## 5. 需求输入与访谈

### 5.1 缺口检查维度

- 业务目标、核心用户和成功指标。
- 业务流程、上下游系统、外部依赖和数据来源。
- 峰值 QPS/并发、吞吐、数据规模、实时性和增长预期。
- 可用性目标、RTO、RPO、故障域和容灾范围。
- 数据敏感等级、合规、数据驻留地域和网络边界。
- 成本、性能、交付速度之间的优先级。
- 现有技术栈、迁移限制、团队技能和运维能力。
- AI、音视频、大数据等领域特有指标。

### 5.2 追问判定

只有当不同答案会改变以下任一结果时才追问：

- 产品或服务类别。
- 地域、可用区、网络边界或容灾拓扑。
- 同步/异步数据流、存储类型或一致性选择。
- 安全、合规、身份权限或审计控制。
- 容量、弹性或成本模型。
- 实施阶段或迁移路径。

默认最多进行两轮追问。用户无法回答或两轮后仍缺失的信息转为显式假设，并说明不同答案会触发的架构分支。

## 6. 场景路由

需求可以同时携带多类标签：

```text
场景：AI_AGENT、CLOUD_NATIVE、BATCH_DATA、REALTIME_DATA、DATABASE、STORAGE、MEDIA、EDGE
质量：LOW_LATENCY、HIGH_THROUGHPUT、HIGH_AVAILABILITY、DISASTER_RECOVERY
约束：PRIVATE_NETWORK、DATA_RESIDENCY、REGULATED、COST_SENSITIVE、MIGRATION
```

主 Skill 根据标签加载最小必要的领域资料。单领域简单需求在主上下文完成；涉及两个以上互不依赖的产品族时，可并行调度对应 subagent。跨领域冲突由主 Skill 裁决，并保留取舍理由。

## 7. Subagent 合约

### 7.1 requirements-analyst

输入：原始需求及已知上下文。  
输出：已知事实、需求缺口、会改变架构的关键问题、可安全采用的默认假设。  
限制：不选择具体产品，不扩展无关访谈。

### 7.2 product-researcher

输入：待验证能力、产品族、地域和动态事实清单。  
输出：事实、官方 URL、页面类型、查询日期、适用范围、冲突或不确定性。  
限制：官方资料优先；第三方资料不能证明关键产品能力。

### 7.3 domain-architect

输入：业务标签、约束、经核验的产品能力和领域边界。  
输出：领域组件、数据流、候选产品、选择理由、替代方案、切换条件和风险。  
限制：不得假设其他领域已经解决共享依赖。

### 7.4 security-reliability-reviewer

输入：整合后的候选架构、数据分类、网络边界和 SLO。  
输出：身份权限、网络隔离、加密、密钥、审计、内容安全、单点故障、RTO/RPO 和容灾缺口。  
限制：高安全或高可用标签存在时必须执行独立评审。

### 7.5 finops-reviewer

输入：候选架构、用量假设和成本优先级。  
输出：成本驱动项、测算公式、优化杠杆、成本风险和需要补充的数据。  
限制：缺少官方价格或用量时不得生成精确金额。

### 7.6 主 Skill

负责去重、解决冲突、统一术语、保证证据链、生成最终输出并判定是否达到生产就绪标准。subagent 只返回结构化中间分析。

## 8. 官方资料与时效策略

证据等级：

- A 级：火山引擎官方产品文档、产品页、价格页、SLA、合规与安全资料。
- B 级：火山引擎官方案例、白皮书、官方代码仓库。
- C 级：第三方资料，仅用于发现线索或补充非关键实践。

产品存在性、核心能力和架构关键限制需要 A 级证据。价格、地域、规格、配额、SLA、版本状态和促销属于动态事实，必须在线查询并标注查询日期。Skill 内置的 `product-catalog.md` 只保存产品族、稳定能力标签和官方入口。

官方页面冲突时，优先采用范围更具体且更新日期更近的内容；若无法确定优先级，保留冲突并要求官方确认。

官方基线入口：

- [火山引擎文档中心](https://www.volcengine.com/docs/86403/1829870?lang=zh)
- [火山方舟文档](https://www.volcengine.com/docs/82379/66619f8df281250274ef4f88?lang=zh)
- [火山引擎云信任中心](https://www.volcengine.com/trust/security)

## 9. 统一输出契约

完整方案按以下顺序输出：

1. 执行摘要：推荐方案、主要取舍和适用边界。
2. 已知条件、假设与待确认项。
3. 架构决策记录：决策、理由、备选方案和未采用原因。
4. Mermaid 逻辑架构图。
5. 地域、可用区、VPC、子网、公网入口和容灾关系组成的部署拓扑。
6. 编号的端到端数据流，包含同步/异步、协议、数据类型、存储和失败处理。
7. 产品映射表：能力、推荐产品、原因、备选产品、触发替换条件。
8. 非功能设计：容量与弹性、可用性、RTO/RPO、安全合规、可观测性、性能和成本。
9. PoC、最小生产版本和规模化三个阶段的实施路线图与验收标准。
10. 风险与验证计划：概率、影响、缓解措施、责任方和验证方法。
11. 官方依据、查询日期和信息时效说明。
12. 需求、架构、安全、可靠性、成本和证据六维完整度评分。

任一关键维度不足时，输出必须明确说明方案不是生产就绪版本。

## 10. 错误处理与降级

- 无网络：允许生成概念架构；所有当前产品能力标记为“未在线核验”。
- 官方页面不可访问：记录失败页面和查询时间，将相关结论列入待验证项。
- 无精确匹配产品：描述所需能力，不强行填入产品名称。
- subagent 结果冲突：展示冲突事实、证据和主 Skill 的裁决理由。
- 关键需求缺失：输出条件式架构和分支，不宣称生产就绪。
- Mermaid 生成失败：保留组件清单和文字数据流，并指出图形交付未通过校验。
- 校验脚本失败：修复缺失结构后再交付，不把脚本通过等同于架构正确。

## 11. 测试策略

### 11.1 基线与前向测试

对每个测试场景，先让未加载 Skill 的独立 agent 生成方案并记录缺陷，再让加载 Skill 的独立 agent 执行相同请求。测试上下文只提供场景和待测 Skill，不泄露预期答案或已发现问题。

代表性场景：

1. 企业知识库问答与工具调用 Agent。
2. 高并发互联网 API 与多可用区云原生部署。
3. 实时采集、流批处理和交互分析。
4. 直播、点播、转码、分发与内容安全。
5. 包含 ASR/TTS、方舟、业务系统和数据分析的智能客服。
6. 金融敏感数据、专网接入、审计和容灾。

### 11.2 自动校验

`validate-deliverable.py` 检查：

- 必要章节和产品映射字段。
- 至少一个有效 Mermaid 代码块或明确的降级说明。
- 假设、风险、来源和查询日期。
- 安全、可靠性、成本和可观测性覆盖。
- 动态事实是否有官方来源和日期。
- 是否存在禁止的无依据“生产就绪”声明。

### 11.3 验收条件

- Plugin 与 Skill 结构验证全部通过。
- 六个场景均可生成符合统一契约的完整输出。
- 不出现无依据的价格、SLA、地域、规格或配额。
- 至少五个场景正确识别会改变架构的关键需求缺口。
- 高安全或高可用场景触发独立评审。
- 无网络或资料不可达时明确标出未核验事实。
- 前向测试发现的新缺口完成修订并重新验证。

## 12. 实施顺序

用户批准本设计后：

1. 编写实施计划和测试场景。
2. 运行无 Skill 基线测试并记录真实失败模式。
3. 使用官方脚手架创建 Plugin 和 Skill。
4. 编写最小主流程、输入输出契约和领域参考。
5. 实现结构校验脚本及其测试。
6. 运行结构验证和六个前向测试。
7. 根据失败模式修订并回归验证。
8. 交付可分享的插件目录及验证结果。

## 13. 已知边界

当前设计确认 Codex 可使用 Skill，并在运行时具备 subagent 协作能力；但公开 Codex 手册在本次查询中返回 HTTP 403，未能从官方手册确认“插件内分发自定义 agent TOML”的稳定规范。因此第一版不依赖该机制，而把 subagent 角色定义为 Skill 内的运行时协议。这一选择同时降低安装耦合并保留未来扩展空间。
